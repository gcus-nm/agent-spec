# 汎用タスクライフサイクル

## 1. タスク契約を作る

依頼から次の4点を抽出します。不足があっても安全な仮定で進められる場合は進め、結果を
大きく変える選択だけを確認します。

- Goal: 何を実現するか
- Context: 関係するファイル、文書、エラー、事例
- Constraints: 安全、互換性、品質、期限、変更禁止範囲
- Done when: テスト、挙動、成果物など、完了を判定する条件

## 2. 依頼種別を判定する

- 説明・調査: 読取と根拠提示まで。変更しません。
- 診断: 原因を特定し、証拠と修正案を示します。依頼がなければ修正しません。
- 変更・実装: 必要な変更と検証まで行います。
- レビュー: 重大度順の指摘を中心にし、明示依頼がなければ修正しません。
- 監視・待機: 指定状態になるまで適切な間隔で確認します。

## 3. コンテキストを絞る

- ルート指示、対象に近い指示、関連する索引を先に読みます。
- ファイル一覧やシンボル概要から候補を絞り、必要な本文だけを読みます。
- 最新の外部仕様が必要なときは、公式文書や一次資料を確認します。
- 大規模・曖昧・高リスクな変更は、実装前に計画と検証方法を明確にします。

## 4. 実行する

- 既存差分を確認し、タスクと無関係な変更を避けます。
- 小さく一貫した単位で変更し、必要に応じて関連テストを追加・更新します。
- 新しい依存関係、公開API変更、移行、外部送信などはスコープを確認します。

## 5. 検証する

- 対象に対応するテスト、リンター、フォーマッター、型検査、ビルドを実行します。
- 実行できない検証は、理由と代替確認を記録します。
- 最終差分をレビューし、要求との対応、意図しない変更、秘密情報の混入を確認します。

## 6. 引き渡す

- 達成した結果を先に伝えます。
- 変更ファイルと重要な判断だけを列挙します。
- 実行した検証と結果、未実施の検証、既知の制約を明示します。
- ユーザーが次に行う必要がある操作だけを案内します。

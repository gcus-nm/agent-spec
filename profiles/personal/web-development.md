# Web開発

## 実行・配布

- Webサービスを新規作成するときは、ユーザーまたは対象プロジェクトから明示的な指定が
  ない限り、Dockerコンテナとしてビルド・実行できる構成を既定とします。
- Dockerイメージの定義、不要ファイルの除外、ビルド・起動手順を成果物へ含め、
  コンテナが正常に起動することを検証します。
- 既存のWebサービスを変更するときは、そのプロジェクトの実行・配布方式を優先し、
  明示的な依頼なしにDocker構成へ移行しません。

## API、CLI、AI操作

### 設計

- 業務データを操作するバックエンドを新規作成するときは、運用とデータ投入に必要な
  主要操作をWeb UIだけに閉じず、認証されたAPIと、そのAPIを呼び出すCLIからも実行できる
  構成を既定とします。対象外にする操作がある場合は、その理由を設計文書へ記録します。
- 業務ルールの正本はバックエンドのApplication Service、外部インターフェースの正本は
  OpenAPIなどの機械可読なAPI契約とします。Web、CLI、必要に応じてMCPツールでAPIクライアント
  またはApplication Serviceを共有し、同じ業務ロジックを実装し直しません。
- ブラウザーからCLIを経由させず、WebフロントエンドはHTTP API、BFF、またはサーバー側
  ハンドラーを通じてApplication Serviceを利用します。WebサーバーからCLIを子プロセスとして
  起動する構成は、既存の外部CLI以外に統合手段がない場合など、理由が明確な場合に限定します。
- 認証、認可、入力検証、状態遷移、冪等性はバックエンドで強制し、Web UIやCLIだけの制御へ
  依存しません。WebとCLIの各経路で同じ制約と結果になるようにします。
- 遠隔利用するCLIはAPIの薄いクライアントとします。マイグレーションや修復など、デプロイ環境
  内でだけ行う管理コマンドは、公開CLIと分離し、実行対象と同じリリース、コード、設定を使います。

### AIが操作するCLI

- CLIは対話なしで完結できるモードを備え、引数、ファイル、または標準入力から入力を受け取れる
  ようにします。コマンド名、オプション、終了コードを安定させ、`--help`に使用例を含めます。
- 成功結果とエラー詳細を機械処理できるJSONで出力するオプションを設け、進捗メッセージと
  データ出力を分離します。エラーには、失敗した対象、理由、再試行可否を含めます。
- 書き込み操作にはdry-runと変更件数・差分の要約を用意します。本番環境や破壊的操作では、
  対象環境と操作内容を明示する確認引数なしに実行しないようにします。
- 再試行で重複更新が起きないよう、冪等性キー、upsert、または同等の仕組みをAPIとCLIで
  提供します。部分失敗した一括処理は、成功済みと未処理を識別できるようにします。
- 認証情報はコマンド引数、URL、標準出力、ログへ含めず、最小権限の資格情報を標準の
  資格情報ストアまたは秘密情報管理から取得します。変更操作には実行主体と対象を監査記録へ
  残します。
- 対象のAI環境がMCPに対応し、CLIより型付きツールの方が安全に操作できる場合は、同じAPI
  クライアントを使う薄いMCPツールを追加できます。入力・出力スキーマ、読取専用・破壊的・
  冪等性の性質、確認が必要な操作を明示します。

### データ投入と検証

- 少量データは通常のAPI操作で扱い、大量データはファイルを受け付ける非同期Import Jobを
  優先します。CLIはジョブID、進捗、行単位のエラー、再開方法を取得できるようにします。
- WebとCLIの代表操作について、認証・入力検証・業務結果が一致することをテストします。
  CLIでは少なくともヘルプ、JSON出力、成功・失敗の終了コード、dry-runで状態が変わらないこと、
  冪等な再実行、監査記録を検証します。
